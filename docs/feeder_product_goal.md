# Feeder — Product Goal & Architecture

更新日期：2026-09-21  
状态：以 Jev 均分控制模拟 Feed 的最新目标；规划内容不等于当前已验证效果。

## 1. 核心目标

Feeder 是用户掌控的跨来源内容发现与稍后阅读产品。它以 Jev 对候选标题与用户兴趣的 1–10 相关度评分为依据，**模拟社交平台可能提供、而用户希望获得的 Feed**。用户可手动选择目标均分 **1–10 中任意整数**；数字越小，筛选越松，越可能混入相邻主题或弱相关视频与信息。Feeder 逐批获取并评分真实候选、反复重组本产品的 Feed，直到达到所选平均值或当前合规候选耗尽。必须显示实际平均值、评分数量、是否达标、模型不可用或候选不足；不得靠伪造条目或分数凑数。

这里的均分是 **展示条目的 Jev 标题相关度算术平均值**，不是平台官方指标。至少五条有效且置信度足够的候选才称为“达标”；最多展示十二条。为避免靠明显无关内容凑均分，每条显示内容的分数不得低于 `max(1, 目标均分−3)`。更低目标应允许较低分的候选进入，但屏蔽来源、标签和用户明确排除仍是硬约束。Jev 只评分标题，不核验视频内容，也不抓取或执行平台动作。用户的兴趣属于用户，而不是某一个内容平台。**改变 YouTube、Bilibili 等平台的原生推荐，不是产品目标或验收条件。**

Feeder 不托管外部视频，不自动播放或刷观看信号，也不依赖平台点赞、订阅或浏览器自动化才能提供核心价值。用户可在来源网站观看；仅在来源允许时嵌入内容。

## 2. 产品闭环

```text
用户明确选择/排除兴趣 → 兴趣标签图与用户权重 → 来源允许的候选采集
→ 元数据规范化与去重 → Feeder 站内个性化排序 → 主 Feed
→ 打开来源 / 稍后读 / 隐藏 / 不感兴趣 → 渐进更新兴趣 → 下一轮发现
```

“打开”仅代表点击跳转；除非有独立、获准且可核验的计量路径，不得称为观看或完成观看。Feeder 的保存、隐藏和不感兴趣只影响 Feeder，不向外部平台写入反馈。

## 3. 用户界面与兴趣模型

主 Feed 卡片按实际可得字段显示标题、来源、创作者、缩略图、发布时间、简介、时长和标签；缺失的字段保持缺失，不能编造。提供 `Open`、`Save for Later`、`Hide`、`Not Interested`，并以 `Why this is here` 解释本产品的推荐依据。`Save for Later` 是强正反馈，但保存不等于已阅读或喜欢。用户可查看、调整和删除兴趣与保存记录。

用户从显式选择的标签开始，逐步构建相邻主题关系。每个标签有**用户专属的标签 JEV（兴趣权重）**，用于确定来源检索优先级和站内排序；这是新目标的数据概念，不预设必须由某个模型生成。界面不展示逐标签权重滑杆；用户通过选择或移除兴趣、反馈及单一 Relevance 目标滑杆控制结果。旧权重数据继续兼容读取。屏蔽标签和来源是硬约束，不能被高分或探索配额绕过。新用户或证据不足时以显式选择为准，不能声称系统已经学会偏好。

兴趣的主要管理入口仅位于 Discover 的 `For you` 视图，不占用工作台导航侧栏，也不在 `Sources` 视图显示。`For you` 提供可组合的内容匹配规则：命中至少一个已选主题、包含所有已选主题、排除带有未选主题的内容。后两项分别判断交集是否完整、内容已识别的兴趣标签是否超出已选集合；公开来源只依赖实际采集到且可映射到兴趣目录的标签，不能把未标注内容推断为匹配。显式屏蔽始终优先，收藏记录不因发现筛选而删除。

Jev 对单条标题与用户 tags 的相关度评分，和内部用户标签 JEV（兴趣权重）是两个不同概念。模拟 Feed 只把真实 Jev 评分计入均分；模型未配置、调用失败或低置信度时显示不可用或未达标，不用本地排序值冒充 Jev。基本收藏与公开来源浏览仍可使用。

## 4. 两阶段发现与排序

**候选采集。** 标签 JEV、内容新鲜度、来源能力、配额与探索需求共同决定标签查询优先级；实际调用量以每个来源当时的限额和返回结果为准，不承诺固定候选数量。JEV 决定检索资源分配，不能直接充当每条内容的最终分数。优先复用已存在的 arXiv、GitHub、Hacker News 采集，以及用户提供的公开 TikTok/X 单条链接解析；这些能力不是跨站搜索或视频源全覆盖。YouTube 官方搜索/元数据、Bilibili、Reddit 等只在各自的访问路径、使用条款、字段和存储规则核实并实现后才列为可用来源。某个来源不可用时，其他来源仍应工作。

Discover 的 `Sources` 来源卡片是操作按钮：进入页面和切换板块不触发采集，用户点击具体来源后才读取该来源。arXiv、GitHub、Hacker News、已配置的 YouTube 与公开 Bilibili 搜索可按来源单独采集。TikTok、X、Instagram 尚无完整来源适配，其选项暂时从 Sources、Connections 和屏蔽来源界面隐藏；既有本地数据不删除。Bilibili 对同一兴趣并行搜索中英文标签名称，按 BV 号去重；公开接口限制请求时如实显示来源错误。YouTube 缺少 key 时在其配置状态下提供密码输入框，用户提交后由本机服务进程临时保存并按已选兴趣搜索；不在浏览器持久保存或回显 key，重启后需重新输入。`For you` 的批量采集也由明确的按钮触发，不在页面打开时后台启动。

学术来源新增 Google Scholar，通过 SerpApi 的 `google_scholar` 搜索接口按最多两个已选兴趣读取最多 20 条论文候选。复用 `/api/harvest`、现有来源健康状态、Jev 评分和资源保存流程。没有 key 时显示配置入口，没有兴趣时提示选择兴趣；来源失败不影响其他来源。网页配置仅允许本机同源请求，key 只保存在服务进程内存；服务器也可通过 `SERPAPI_API_KEY` 配置。来源说明明确标注 SerpApi，保留真实论文链接和元数据；只有年份时不虚构完整发布日期。

**模拟 Feed。** 先应用排除、去重与来源规则，再逐批用 Jev 给允许评分的候选标题打分。对所有已选兴趣都只凭标题判断主要主题：检索命中、来源或未传入的标签不能代替主题证据；标题主要讲其他主题、只偶然含兴趣词或意思含糊时不得给高相关分。多个兴趣取标题证据最充分的一项，混合主题按其主次评分。以高分候选建立起始 Feed，在保持均分不低于用户目标的条件下逐步加入较弱候选；目标较低时能看到更宽的主题范围。均分不足、少于五条、低置信度或服务错误应如实显示。其他本地排序值只用于候选处理，不得混入 Jev 均分或称为平台官方指标。每一来源的衍生数据、跨来源混用、展示及保存须先通过该来源政策审查。未经确认的字段或评分项禁用，不以模型推断补齐受限数据。

**YouTube 展示边界。** 可通过已配置的官方 YouTube Data API 搜索公开视频链接；程序把符合可嵌入状态且非 Made for Kids 的链接转换为 YouTube 隐私增强模式的嵌入地址，由官方播放器在主页展示视频标题与封面，且关闭自动播放。未确认可嵌入的视频只显示 API 返回的封面、标题和回源链接。没有 API key 时显示配置状态，不爬取 YouTube 首页或私有接口。YouTube 开发者政策限制由 API 元数据生成衍生评分；当前实现将 YouTube 搜索卡片与 Jev 均分分开展示，不把其标题传给 Jev。若未来要把它纳入 Jev 均分，必须先取得适用政策依据或许可。

**Bilibili 展示与评分。** 只读取公开搜索返回的标题、封面、UP 主、标签等元数据；卡片点击后才加载官方外链播放器，不下载视频或操作平台账号。候选标签依据公开文本及现有中英文兴趣对照匹配；Jev 仅对标题和用户兴趣的语义相关度评分，同一兴趣的中英文名称作为同一项传入，不能把语言差异直接判成零相关。所有兴趣都使用上述标题主要主题准则，不能因为内容出现在某个兴趣的搜索结果里就给高分。实际分数仍以 Jev 返回值为准，不做本地强制提分。

默认保留一个可调整的探索窗口（目标范围约 10–20%，不是固定保证），用于邻近或低置信度主题；只在有合规候选、且不违反明确排除条件时填充。结果不足时允许空位或空 Feed，不伪造内容。

## 5. 反馈与可解释性

用户明确行为和系统行为分开保存：保存为强正信号，打开为较弱的兴趣线索，隐藏为负信号，不感兴趣为较强负信号。一次点击不能大幅改写用户画像；可采用上限、时间衰减及撤销机制，逐步更新标签、来源、创作者与内容类型偏好（仅在有可靠元数据时）。自动采集、预览、模拟器和 Agent 动作都不能算作用户反馈。

`Why this is here` 显示实际采用的用户标签、相邻主题、来源和新鲜度等理由，并注明是 Feeder 的解释，不暗示外部平台背书。用户能直接调整兴趣，而不需要通过大量点击“训练”系统。

## 6. 来源与共享候选池

来源适配器应声明自身支持的能力（例如搜索、公开列表、单链接解析、元数据补充），而不是要求每个平台必须实现同样的方法。现有采集器保持原样复用，只有缺少的能力才增量扩展。采集、来源健康状态、配额、去重、来源归属和有效期与用户画像分离。未来多用户部署可按标签/来源共享合规候选池，再按用户排序；本地单用户版本不需要为了这个设想先引入全局调度和云端数据库。

只存储来源许可的外部 ID、链接与必要元数据，并遵守来源对归属、缓存、删除和更新的要求。打开原始来源优先；嵌入仅在许可且技术上可用时提供。粘贴用户自己的 HTTP(S) 链接仍可作为本地稍后读，不代表 Feeder 已取得页面元数据或平台搜索权限。

## 7. MVP 与实施次序

1. 直接进入工作台，在 Discover 管理兴趣与显式排除；保留旧兴趣引导源文件供未来账号注册使用。复用公开采集、资源库与 CLI，并保持已有 API 合同和数据兼容性。
2. 明确用户标签 JEV（兴趣权重）与相邻标签图，保留本地持久化；界面只提供一个 Relevance 目标滑杆，不要求用户逐标签调整权重。
3. 在已有采集结果之上规范化候选、去重并建立 Jev 标题评分与 1–10 均分控制的主模拟 Feed；先以实际可用的公开来源验证端到端闭环。
4. 让站内 `Open`、`Save for Later`、`Hide`、`Not Interested` 驱动有界反馈与下一轮排序；增加理由、探索和可撤销性。
5. 逐个验证并增加新的来源能力；YouTube 搜索/元数据需单独处理 API 配置、查询配额、政策、存储与归属。不要因某个来源受阻而阻塞核心产品。
6. 只有本地闭环被真实使用验证后，才考虑共享候选池、持久化后端、多设备与更复杂的学习方法。

旧的 YouTube 点赞/播放 Runner、Bilibili 平台操作和原生 feed 前后评估不是 MVP 的依赖或验收门槛。旧合同和设计材料可暂时保留以免破坏兼容性，但只能标成预览、历史设计或独立实验；任何未来平台写操作都需重新取得明确授权、许可和逐项核验。

## 8. 成功标准与现状边界

成功的衡量对象是 **Feeder 自己的下一轮 Feed**：明确屏蔽项是否被排除、推荐理由是否可信、用户是否认为候选值得打开或保存、重复与单一来源是否得到控制，以及反馈后排序是否有可测改进。保存/打开率仅是行为指标，不自动等于内容质量或因果改善；使用真实用户评估、留出/对照和来源健康指标检验。

截至 2026-09-21，本地原型已复用兴趣选择、公开来源采集和资源库，并接入 Jev 逐条标题评分、1–10 均分目标、逐批模拟和达标状态。内部标签权重、附近主题、本地去重与排序、理由及有界可撤销反馈继续保留；用户调整相关度只用一个滑杆。YouTube 官方搜索和标题/封面卡片已写入代码，但本机没有 `YOUTUBE_API_KEY`，真实搜索未验证；YouTube 不计入 Jev 均分。当前标签关系只是同目录邻近，不是学习出的完整标签图；真实用户的 Feed 质量、来源多样性和因果改善也未验证。

来源政策核对入口：[YouTube `search.list`](https://developers.google.com/youtube/v3/docs/search/list)、[配额概览](https://developers.google.com/youtube/v3/getting-started)、[开发者政策](https://developers.google.com/youtube/terms/developer-policies)。配额和政策可能变化；实际接入前按当前文档及项目控制台重新核实，特别审查站内衍生评分和跨来源展示。
